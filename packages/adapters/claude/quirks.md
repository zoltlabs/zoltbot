## Desktop parity assumptions

Shapes marked "2.1.42 bundle" were read from the installed `@anthropic-ai/claude-code` 2.1.42 `cli.js`, not from a live run. Everything else here is synthetic and needs the live canary. Parsing ignores unknown fields and fails closed.

* Permission suggestions (2.1.42 bundle): `can_use_tool` carries `permission_suggestions` as Agent SDK PermissionUpdate values (`addRules`, `replaceRules`, `removeRules`, `setMode`, `addDirectories`, `removeDirectories`, destinations `userSettings`, `projectSettings`, `localSettings`, `session`, `cliArg`). The adapter forwards only `addRules` with behavior allow, and `setMode` to a mode the profile allows other than plan. It always forces destination `session`, so nothing reaches a settings file (I11). Directory grants are never forwarded because they widen the filesystem boundary. The 2.1.42 request has no `cwd`; rule suggestions use the session cwd.
* Rule suggestions: Bash needs a native `ruleContent` prefix of at least two words without wildcards that covers the current command. WebFetch suggests the exact URL host. MCP tools suggest the full `mcp__server__tool` name without the `mcp` matcher field, because the daemon's approval operation does not fill `mcp` yet. Edits suggest the exact workspace-relative file.
* Plan review: approval sends `updatedPermissions: [{type: "setMode", mode, destination: "session"}]` with `acceptEdits` or the profile base mode (`default`, or `bypassPermissions` for full access). Accept with feedback appends `## Reviewer notes` to `updatedInput.plan`. Delivery relies on the ExitPlanMode tool result echoing the approved plan to the model. This needs the live canary.
* Modes: `system/init.permissionMode` and a `system/status` frame with `permissionMode` report mode changes. The status frame shape is assumed. `mode.changed` is emitted only after Claude confirms the mode: a successful `set_permission_mode` (which 2.1.42 answers with `{mode}`), or an init or status frame. A `setMode` update inside a permission answer has no acknowledgement and may be ignored, so the adapter repeats it through `set_permission_mode` and reports it only on success. `capabilities.safeModes` lists default, plan, and acceptEdits (read only: default and plan); other modes widen permission and need a confirmed human request.
* Bypass availability (2.1.42 bundle): bypassPermissions is selectable only when Claude was launched in it or with `--allow-dangerously-skip-permissions`. Full access sessions always pass that flag, so a session relaunched in default after a mode switch can still return to bypassPermissions. Other profiles never pass it (I10).
* Session grants: a `setMode` suggestion is forwarded only for acceptEdits. When the label naming every grant would exceed 200 characters, allow_session is not offered. Only native prefix rules (`npm test:*`) become command rule suggestions; an exact rule would turn into an argv prefix and allow longer commands.
* Elicitation: the 2.1.42 bundle has no SDK elicitation control request. The adapter assumes `control_request` subtype `elicitation` with `mcp_server_name`, `message`, `mode` (`form` or `url`), `requested_schema`, and `url`, answered with `{action, content}`. Unsupported schemas, non-HTTP URLs, and requests outside a turn are declined.
* Manual compaction: `/compact [instructions]` is sent as a stream-json user message and treated as a turn: `turn.started`, `compaction started`, `compact_boundary` (trigger manual), then `result`. That result frame and the behavior on a session without history are unverified.
* Background tasks: `system/task_notification` with `task_id`, `status` (completed, failed, stopped), `output_file`, and `summary` exists in the 2.1.42 bundle, as do the Bash result text "Command running in background with ID: X. Output is being written to: P" and `tool_use_result.backgroundTaskId`. `task_started` and `task_progress` system frames are assumed. Task frames are handled between turns. If Claude starts a model turn by itself after a task notification, its other frames are still dropped; see BL-009. The idle timer keeps the process alive while a task runs, because closing it ends the task. For the same reason, model and name changes, which relaunch the process, fail with `session_busy` while a task runs. A rewind holds the session: sends queue and compaction fails with `session_busy` until it ends.
* stop_task (2.1.42 bundle): `{subtype: "stop_task", task_id}` answers success or a control error. The adapter marks the task stopped on success; a later notification may refine it.
* Rewind (2.1.42 bundle): SDK file checkpoints need `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=true`. `rewind_files {user_message_id, dry_run}` returns `{canRewind, error?, filesChanged?, insertions?, deletions?}` for a dry run. A real rewind returns only `{canRewind: true}` or a control error, so the adapter dry runs first to report files. A client-supplied user message `uuid` becomes the prompt uuid; the replayed user frame's uuid is preferred when present. Turn to uuid mapping is in memory, so turns from before a reopen report `unsupported_rewind`. Checkpoint survival across a native resume is unverified.
